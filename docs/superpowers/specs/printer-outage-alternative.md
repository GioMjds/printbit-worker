# Specification: Printer Outage Alternative (Admin Recovery Control Plane)

## 1. Overview & Architectural Role

The **Printer Outage Alternative** introduces a secure, administrator-triggered printer recovery control plane to the `PrintBit.HardwareService` worker. It enables administrative tools (such as the kiosk maintenance UI via the Node.js backend) to inspect printer health diagnostics and perform a single, bounded restart of the native Windows Print Spooler service (`Spooler`) without manipulating active print jobs, modifying kiosk lock-down restrictions, or shelling out to external scripts.

### Core Principles

1. **Stateless Worker**: The C# hardware service processes each command synchronously and independently; it maintains no durable recovery history or audit database.
2. **Node-Owned Orchestration**: The local administrative Node.js service owns authorization, maintenance UI flow, customer transaction gating, and durable persistence of recovery history.
3. **Bounded & Deterministic**: Spooler service transitions are bounded by a strict 30-second timeout, followed by a 10-second polling recheck window.
4. **Physical Fault Avoidance**: Hardware conditions (paper out, paper jam, cover/door open, ink out, service/Epson popups) immediately return `manual_intervention_required` and bypass spooler restart.
5. **Mutual Exclusion with Printing**: A singleton operation coordinator (`IPrinterOperationCoordinator`) prevents recovery operations from executing concurrently with print jobs. Recovery returns `worker_busy` without waiting or interrupting the active print.
6. **No-Job-Operation Policy**: The recovery control plane never manipulates, cancels, or deletes spooler print jobs, never touches spool files (`*.spl` / `*.shd`), never resets PnP USB devices, never launches Epson configuration utilities, and never kills processes (`taskkill`). Automatic destructive recovery on print timeouts is completely removed.

## 2. Command Pipe Architecture & Security

### Named Pipe Endpoint

- **Pipe Name**: Configured via `IpcSettings.WorkerCommandPipeName` (default: `printbit-worker-commands`).
- **Framing**: Line-delimited UTF-8 JSON (`\n` separated).
- **Size Limit**: Enforced maximum of `IpcSettings.MaxMessageBytes` (default: 8192 bytes). Payloads exceeding this limit are rejected before parsing with outcome `invalid_request`.
- **Connection Lifecycle**: Single-shot request/response. The client connects, sends exactly one JSON line, reads exactly one JSON response line, drains the pipe, and the server closes the connection.

### Restrictive Windows DACL

Because the kiosk worker runs as the unprivileged interactive identity `desktop-jhtg0bm\printbit` and administrative tasks run under elevated identities (such as `desktop-jhtg0bm\admin` or `LocalSystem`), the named pipe security descriptor is explicitly configured using `NamedPipeServerStreamAcl.Create` and `WorkerCommandPipeSecurity`:

| Identity / SID | Access Mask | Rationale |
|---|---|---|
| Current Service Process Identity | `PipeAccessRights.FullControl` | Server pipe owner and listener lifecycle |
| `LocalSystem` (`SecurityIdentifier(WellKnownSidType.LocalSystemSid, null)`) | `PipeAccessRights.FullControl` | System service maintenance and automation |
| `BUILTIN\Administrators` (`SecurityIdentifier(WellKnownSidType.BuiltinAdministratorsSid, null)`) | `PipeAccessRights.ReadWrite` | Administrative Node.js service running as administrator |

**Explicit Exclusions**:
- `WorldSid` (`Everyone`) and `AuthenticatedUserSid` are strictly omitted from the DACL.
- Unprivileged kiosk users or compromised browser sandbox identities receive `UnauthorizedAccessException` and cannot connect to query status or trigger recovery.

## 3. Command Request & Response Schema

### Inbound Commands (Node -> Worker)

Single-line JSON payload:

```json
{
  "requestId": "req-98234-abcd",
  "type": "GetPrinterRecoveryStatus",
  "timestampUtc": "2026-09-02T01:45:00.000Z"
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `requestId` | string | Yes | Non-empty correlation identifier generated by Node. Preserved verbatim in the response. |
| `type` | string | Yes | Command type enum: `"GetPrinterRecoveryStatus"` or `"AttemptPrinterRecovery"`. Case-insensitive deserialization. |
| `timestampUtc` | string | No | Optional ISO-8601 UTC timestamp of request generation. |

Requests with empty or missing `requestId`, missing or unknown `type`, invalid JSON, or exceeding `MaxMessageBytes` are rejected with `outcome: "invalid_request"`.

### Outbound Responses (Worker -> Node)

Single-line JSON payload:

```json
{
  "requestId": "req-98234-abcd",
  "type": "AttemptPrinterRecovery",
  "outcome": "recovered",
  "action": "RestartSpooler",
  "spoolerState": {
    "isRunning": true,
    "status": "Running",
    "errorMessage": null
  },
  "printerState": "Healthy",
  "issueKind": "None",
  "message": "Windows Print Spooler restarted and printer is now healthy.",
  "startedAt": "2026-09-02T01:45:00.120Z",
  "completedAt": "2026-09-02T01:45:06.450Z"
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `requestId` | string | Yes | Echoes the request correlation ID (or empty string if unparsable). |
| `type` | string | Yes | The requested command type (`"GetPrinterRecoveryStatus"` or `"AttemptPrinterRecovery"`). |
| `outcome` | string | Yes | Typed outcome enum (see table below). |
| `action` | string? | No | The action executed (`"RestartSpooler"` or `null`). |
| `spoolerState` | object? | No | Current Spooler status snapshot: `{ "isRunning": bool, "status": string, "errorMessage": string? }`. |
| `printerState` | string? | No | Typed printer state: `"Healthy"`, `"Offline"`, `"Unavailable"`, or `"Fault"`. |
| `issueKind` | string? | No | Typed classification: `"None"`, `"PhysicalFault"`, `"WindowsQueueFault"`, or `"Unknown"`. |
| `message` | string | Yes | User-safe explanation of the result or error. |
| `startedAt` | string | Yes | ISO-8601 UTC timestamp when processing began. |
| `completedAt` | string | Yes | ISO-8601 UTC timestamp when processing ended. |

## 4. Outcome Mapping & Decision Matrix

| Outcome | Trigger Condition | Spooler Restarted? | Action Value | Next Steps |
|---|---|---|---|---|
| `healthy` | Spooler running and printer diagnostic is healthy | No | `null` | Kiosk ready for customer printing. |
| `recovered` | Windows-side fault detected, Spooler restart succeeded, and printer diagnostic rechecked healthy within deadline | Yes | `"RestartSpooler"` | Kiosk restored to healthy operation. |
| `manual_intervention_required` | Physical printer error detected before or after restart (paper out, paper jam, door open, ink empty, service required, or Epson popup dialog) | No / Yes (if detected after) | `null` | Staff intervention required to resolve physical fault. |
| `worker_busy` | Recovery lease cannot be acquired because an active print job or another recovery operation holds the lease | No | `null` | Active print is protected. Node retries after print completion. |
| `restart_failed` | Spooler service failed to stop/start within timeout (30s), transition errored, or final recheck timed out without health | Yes | `"RestartSpooler"` | Escalate to administrator / Windows reboot. |
| `invalid_request` | Malformed JSON, payload > 8192 bytes, unknown command type, or missing request fields | No | `null` | Fix request formatting in Node client. |

## 5. Node Handoff Contract & Operational Requirements

The administrative Node.js service must satisfy the following integration requirements:

1. **Administrative Privilege**: The Node client process must run with administrative tokens (`BUILTIN\Administrators`) to satisfy the command pipe DACL.
2. **Response Timeout Deadline (>= 45s)**: The maximum duration of a worker recovery cycle is bounded by `SpoolerTransitionTimeoutSeconds` (30s) + `HealthRecheckTimeoutSeconds` (10s) + overhead (~5s). The Node client must configure an I/O response deadline of at least **45 seconds** before timing out the connection.
3. **Audit & History Persistence**: Because the C# worker is stateless, the Node service is solely responsible for recording recovery attempts, timestamps, request IDs, and outcomes into durable disk-backed logs or a database for technician auditing.
4. **Transaction Gating**: Node must maintain a system-level lockout preventing user payments, document conversion, or print dispatch whenever printer health is not confirmed healthy or while recovery is in flight.

## 6. Dependency Injection & Service Registration

All recovery components are registered with **Singleton** lifetimes in `Program.cs`:

```csharp
// Configuration
builder.Services.Configure<PrinterRecoverySettings>(
    builder.Configuration.GetSection("PrinterRecoverySettings"));

// Singletons
builder.Services.AddSingleton<IPrinterOperationCoordinator, PrintOperationCoordinator>();
builder.Services.AddSingleton<IPrintSpoolerController, ServiceControllerSpoolerController>();
builder.Services.AddSingleton<IPrinterRecoveryService, PrinterRecoveryService>();

// Hosted Background Service
builder.Services.AddHostedService<WorkerCommandPipeHostedService>();
```

### Configuration Model (`PrinterRecoverySettings`)

```json
{
  "PrinterRecoverySettings": {
    "ServiceName": "Spooler",
    "SpoolerTransitionTimeoutSeconds": 30,
    "HealthRecheckTimeoutSeconds": 10,
    "HealthRecheckIntervalSeconds": 2
  }
}
```
